# Implementation Summary

**What I built.** `llm_judge_evaluation.ipynb` is a small evaluation pipeline that uses the OpenAI API directly. A **chatbot** (`gpt-4o-mini`, temperature 0) answers 5 customer messages for the fictional retailer Northwind Living, using only the company policy in its system prompt. Each reply is then scored in two ways:
- **LLM-as-judge** (`gpt-4o-mini`, temperature 0, JSON output). It uses the judge prompt designed in `evaluation_design.md` (task, 3 criteria, reasoning steps, score anchors) and receives each case's ground truth as the "expected behaviour".
- **Rule-based checks**, using required and forbidden regex patterns from the prompt cards (e.g. never repeat the card number "4111").

For every case the pipeline records the reply, score, reasoning, criteria met, rule result, time, tokens and cost, and saves everything in `evaluation_results.json`. Before the run I tested the judge on one good and one deliberately bad reply (blaming the customer and inventing a voucher). It scored them 5 and 1, as expected.

**Key findings.** The chatbot was **safe**: `policy_accuracy` was met in 5/5 cases, it correctly refused the non-returnable mattress (P2, score 5), it escalated the injury case (P4), and it never invented discounts, phone numbers or promises. It was **often incomplete**: `completeness_next_step` was met in only 1/5 cases. It left out the refund timeline (P1), the advice to seek medical attention (P4) and, most importantly, the **warning not to share card details and the request for an order number (P5)**, which also failed the rule check. It also **over-escalated**, adding "a human colleague will take over" to simple cases (P1-P3), probably because the system prompt stresses escalation. Metrics: average judge score **4.0** (min 3, max 5), rules passed **4/5**, total time **18.8 s** (about 3.8 s per case), **5,872 tokens**, total cost **about $0.0012**.

**The judge was too lenient, so I added a calibration step.** In P1, P4 and P5 the judge's own reasoning said a criterion was not met, yet it still gave a 4, against its own anchors ("one criterion not met = 3"). I therefore compute a **calibrated score** in code: the lower of the judge's score and a cap based on criteria met (3 → 5, 2 → 3, 1 → 2, 0 → 1). This lowered the average from **4.0 to 3.4**, and only P2 keeps a top score. Lesson: the judge's *reasoning* was reliable, but its *numbers* were not, so the final score should be tied to explicit criteria rather than trusted blindly. **Limitations:** only 5 single-turn cases, one run each; the same model writes and judges (self-preference risk); no human labels yet to calibrate against.
